**Evidence (live, 2026-11-22 ~16:10):**
- VPS `pm2 env` for `mexc-dex-arb-ethereum-live`: `SCAN_MIN_GAP_PCT=2`, `MIN_MEXC_VOLUME_USD=10000`, `MIN_DEX_VOLUME_USD=10000`, `TRANSFER_UNIVERSE_MAX=100`.
- Repo `ecosystem.live.config.cjs`: `MIN_MEXC_VOLUME_USD: '20000'`, `MIN_DEX_VOLUME_USD: '20000'`, **no `SCAN_MIN_GAP_PCT`** (so the default 3% from `src/config.ts` would apply).
- md5: VPS `ecosystem.live.config.cjs` = `bdb1280a…`, local = `818d244f…` (different). All other compared files match (`src/scanner.ts`, `src/transfer.ts`, `src/main.ts`, `src/config.ts`, `status-server.mjs`, `ecosystem.arbitrum-live.config.cjs`, `ecosystem.bsc-live.config.cjs` — identical md5s).
- The repo file's own comment still says "MEXC 24h vol >= $20k and DEX 24h vol >= $20k", and its header comment still says "trades only tokens proven profitable in paper" (proven-only was removed for transfer mode on 2026-11-22).

**Concrete risk:** anyone who runs `pm2 delete mexc-dex-arb-ethereum-live && pm2 start ecosystem.live.config.cjs` from the repo (the normal deploy path) silently reverts the live twin to $20k filters and a 3% gap threshold. The twin would then scan a smaller universe and skip the 2–3% gaps it currently trades on — a silent behaviour change with no alert. The arb/bsc configs in the repo already carry the $10k + 2% values, so only the Ethereum live config is stale.

**Fix:** copy the running values into the repo file (`MIN_MEXC_VOLUME_USD`/`MIN_DEX_VOLUME_USD` 10000, add `SCAN_MIN_GAP_PCT: '2'`), fix the two stale comments, and treat "pm2 env must match the repo config" as a deploy checklist item.

### H2 — Telegram 409 conflict: four bots, one token — the /stop kill switch is degraded

**Evidence (VPS logs, last hour, all four bots):**
- `mexc-dex-arb-ethereum` (paper): `telegram poll: telegram getUpdates: Conflict: terminated by other getUpdates request … (retry in 20s)`, then 40s, 80s, 160s.
- `mexc-dex-arb-ethereum-live`: `… (retry in 300s)` — at the maximum backoff.
- `mexc-dex-arb-arbitrum-live` and `mexc-dex-arb-bsc-live`: identical 5s → 10s → 20s → 40s → 80s → 160s backoff chains from 10:05–10:08 UTC.
- Cause (`src/telegram.ts`, `startPolling`): each bot long-polls `getUpdates` with its **own** offset stored in its **own** DB. Telegram allows only one active `getUpdates` per bot token, so three of the four pollers lose every round and back off exponentially (5s → 300s max).

**Concrete risk:**
1. **/stop latency:** a bot in 300s backoff will not see a /stop for up to 5 minutes. /stop only blocks *new* trades (an open transfer finishes by design), and the local risk limits still apply, so the exposure is bounded — but the human kill switch is the operator's main override, and it is currently unreliable.
2. **Duplicate command delivery:** because offsets are per-bot, a command sent once is eventually processed by *every* bot (each replays from its own offset). /stop and /start hitting all four bots is mostly harmless, but /sell and /clear also fire on all four — the three non-owning bots reply "No transfer #N" to the shared chat, and there is **no way to address one chain** (no per-chain command targeting). /cancelnonce would fire on all chains at once.
3. **Log spam:** every poll cycle logs a warning; the signal (a real Telegram outage) is buried.

**Fix (choose one):** a single shared poller that fans commands out to the four processes, or one bot token per twin, or a dedicated command bot. Short-term: note that /stop is "best effort, up to ~5 min" and rely on the local risk limits (daily loss, fail streak) as the real guard.

## Medium

### M1 — Gas is priced with ETHUSDT on every chain (BSC gas overstated ~3.5x)

**Evidence:** `src/transfer.ts:180-181` — `const eth = tickers.get('ETHUSDT'); if (!eth) throw new Error('no ETHUSDT ticker');` — then `ethUsd` is used for *all* gas conversion on the transfer path: `src/transfer.ts:192` (`gasInOutput`), `:335` (`evaluateTransfer` gas), `:662`, `:676`, `:693`, `:718` (`(Number(gasWei) / 1e18) * ethUsd` in sell bookkeeping). The chain profile already carries the right symbol (`src/chains.ts`: BSC `nativeMexcSymbol: 'BNBUSDT'`), and the **inventory** engine uses it (`src/engine.ts:289`: `mid(await this.d.book(this.cfg.chain.nativeMexcSymbol))`) — the transfer engine never got the same treatment. No test covers it: `test/upgrade-chain.test.ts` only asserts `nativeMexcSymbol === 'BNBUSDT'`, not that the transfer tick uses it.

**Concrete risk:** on BSC, gas is paid in BNB (~$950) but converted at the ETH price (~$3,300), so every BSC gas figure is overstated ~3.5x. Measured impact is small because BSC gas is tiny — live BSC `eth_feeHistory` (2026-11-22) shows p50 tip 0.05 gwei, base fee 0, so a swap costs ~$0.01–0.05 real vs ~$0.04–0.18 booked. The observed BSC rejection `WKC: gap 2.34%, size $300.00, exact net -$6.75 (need $0.60)` is driven by the 1.5% drift reserve + fees, not by this bug. So: no trade has been lost to it yet, but BSC PnL is systematically understated and marginal BSC trades are evaluated with the wrong gas. On Arbitrum there is no error (gas token is ETH).

**Fix:** in `transfer.ts` tick(), read `tickers.get(this.cfg.chain.nativeMexcSymbol)` instead of `'ETHUSDT'`.

### M2 — All sends go through public RPCs; no MEV protection anywhere

**Evidence:** VPS `.env` sets `RPC_URL` and `SEND_RPC_URL` to host `ethereum.publicnode.com` (hostname only — the URL was not printed). `src/config.ts` defaults `SEND_RPC_URL` to `https://rpc.mevblocker.io` with the comment "Private RPC for sending: never the public mempool", but the `.env` overrides it. Arbitrum and BSC configs also use public endpoints (`arbitrum.publicnode.com`, `bsc-dataseed.binance.org` — documented in their config comments as "mevblocker is Ethereum-only").

**Concrete risk:** every DEX sell (~$300, KyberSwap) is visible in the public mempool before it mines, so it can be sandwiched. The damage is bounded by `DEX_SLIPPAGE_BPS=30` (0.3% ≈ $0.90 per trade) plus the gas of a reverted retry, and the attacker earns little per $300 trade — but the exposure exists on every live trade on all three chains, and the operator may believe mevblocker is in use. (On Arbitrum/BSC there is no mevblocker equivalent configured at all.)

**Fix:** point the Ethereum live twin's `SEND_RPC_URL` back at mevblocker (or another private RPC); accept the public-mempool exposure on ARB/BSC explicitly, or use a private endpoint there too.

**Evidence:**
- `pm2 list` ~16:10 Dhaka: `mexc-dex-arb-ethereum` and `mexc-dex-arb-ethereum-live` both uptime 45m (started ~15:25 Dhaka). VPS `dist/` was rebuilt at 10:04 UTC (16:04 Dhaka) by the networkFor deploy, which did not restart them.
- Their Telegram tags prove it: eth-live "Bot started" 09:23:42 UTC carries `🔴 LIVE — আসল টাকা` with **no chain suffix**; eth paper carries `📝 PAPER` with no suffix. The arb/bsc twins (started 16:05) carry `🔴 LIVE — আসল টাকা · arbitrum` / `· bsc`.
- Functional impact on Ethereum is nil (for `chain=ethereum`, `networkFor` ≈ `ethNetwork`, stable decimals are 6, the gate already allowed it) — the only visible defect is the missing chain tag, which the operator was told all live messages now carry.

**Concrete risk:** process gap, not a money bug — deploys that rebuild `dist/` do not restart all twins, so running code silently diverges from disk. The next Ethereum-relevant fix would have the same fate. Fix with a plain `pm2 restart` of the two Ethereum twins (code is loaded fresh at process start; no config change, so delete+start is not needed) and add "restart every twin after a build" to the deploy checklist.

### M4 — Risk limits are per-twin, not global (combined daily loss budget is 3× $30)

**Evidence:** `src/config.ts:136-137` — `MAX_TRADES_PER_DAY` default 20, `DAILY_LOSS_LIMIT_USD` default 30; neither is overridden in any ecosystem config or in the VPS `.env`. `src/risk.ts` keeps all state in the twin's own SQLite DB. The repo's own `ecosystem.config.cjs` header already warns about this (round-3 M2: "each keeps its own risk state… each can spend the full daily loss budget").

**Concrete risk:** the three live twins share one MEXC account and one hot wallet but each has its own $30/day loss budget and 20-trade/day cap, so a correlated bad day can lose $90 and open 3× $300 = $900 of transfers at once. The owner was told the combined exposure is 3× $300/cycle; the combined *loss* budget is likewise 3×. This is accepted design, but it should be a conscious number, not an accident of defaults.

### M5 — Startup-failure alerts spam Telegram (one alert per pm2 restart, up to 1000 restarts)

**Evidence:** `src/main.ts:471` — `main().catch` sends `❗ Bot failed to start: …` on **every** startup failure, then `process.exit(1)`; pm2 `autorestart: true, max_restarts: 1000` restarts it. Observed live: the Arbitrum twin sent two "Bot failed to start" alerts ~12s apart (09:40:29 and 09:40:41 UTC) before it was stopped. A persistent startup bug would send dozens of alerts with growing backoff before pm2 gives up.

**Concrete risk:** alert fatigue — a real alert (failed withdraw, stuck transfer) drowns in startup spam. Fix: alert only on the first failure, or throttle startup alerts (e.g. once per 15 min), or set a low `max_restarts` for a failing start.

### M6 — /status on BSC shows a wrong wallet balance (latent until the first BSC sale)

**Evidence:** `src/main.ts:410` (`transferStatus`): `` `MEXC … | wallet ${(Number(eth)/1e18).toFixed(4)} ETH, ${usd(Number(usdc)/1e6)} USDC` `` — the native label is hardcoded `ETH` (should be BNB on BSC) and the stable balance is divided by a hardcoded `1e6` (BSC USDT has 18 decimals). The value comes from `chain.tokenBalance(cfg.usdc)`, which on BSC is the 18-decimal USDT raw balance.

**Concrete risk:** display-only, but the operator reads /status to decide on rebalancing. After the first BSC sale leaves USDT in the wallet, /status will show it ~1e12× too large (e.g. 5 USDT → "$5,000,000,000,000.00 USDC") and the gas token as "ETH". Currently 0 BSC trades, so it shows $0.00 — the bug is latent. Fix: use `this.cfg.chain.nativeMexcSymbol` for the label and the startup `stableDecimals` for the divisor (the same `stableDec()` pattern the transfer engine already uses).

### M7 — Arbitrum L1 fee is not captured in evaluation or booked PnL (known, documented, small)

**Evidence:** `src/config.ts:132` — `L1_FEE_USD` defaults to 0 with the comment "0 on Ethereum/Arbitrum"; no ecosystem config sets it. `src/dex/txsender.ts:274` adds only `rawReceipt.l1Fee` to `gasCostWei`, and `src/dex/chain.ts:70-73` reads only the `l1Fee` field. Arbitrum receipts carry `gasUsedForL1`, not `l1Fee` — the Arbitrum config file itself notes this ("the OP-stack l1Fee capture does not apply to Arbitrum receipts … so live PnL slightly understates gas"). I could **not** verify the receipt fields live: `eth_getTransactionReceipt` on `arbitrum.publicnode.com` returns `{"code": -32602, "message": "Archive requests require a personal token"}`.

**Concrete risk:** each Arbitrum transfer's gas is understated by the L1 data fee of two transactions (approve + swap), typically ~$0.05–0.60 total. Against a ~$6–15 expected net and a 1.5% (~$4.50) drift reserve, this cannot flip a trade from profitable to loss-making on its own, but Arbitrum PnL will read slightly better than reality. Fix: read `gasUsedForL1` from the receipt and price it at the L1 gas price, or set a measured `L1_FEE_USD` for the Arbitrum twin.

`src/dex/txsender.ts:192`, `src/commands.ts:24`, `src/engine.ts:459` tell the operator to "check etherscan" even on BSC/Arbitrum. Cosmetic — the transfer `unknownOutcome` message correctly uses `this.cfg.chain.explorer`. Fix by using the chain's explorer host in those strings.

### L2 — /api/status top-level `dbOk`/`pm2` describe the paper section, not the chain
Verified live: `/api/status?chain=bsc` returns top-level `dbOk:false`, `pm2:{"state":"not-found"}` (that is the *paper* section — no paper bot on BSC, by design) while the nested `live` object correctly has `dbOk:true`, `pm2:{"state":"online","uptime":422507}`. But any API consumer reading the top level will conclude the BSC bot is down. Consider renaming the top-level fields or documenting that they are the paper section.

### L3 — Paper process holds the real private key in memory
The paper twin reads the shared VPS `.env`, which contains `PRIVATE_KEY` (config: `privateKey: mode === 'live' ? str('PRIVATE_KEY') : str('PRIVATE_KEY', '')` — paper falls back to `''` only if unset; it is set). Code review proves paper never calls `send`/`withdraw`/`limitOrder` (`src/transfer.ts` tick: `if (!this.live) return this.recordPaper(best)`; `advance()` only runs on persisted transfers, and the paper DB has none — verified: `data/ethereum.sqlite` has 0 transfers, 25 paper trades). So this is defense-in-depth only: a future paper-mode bug that reached `send` would have a funded key. Consider a keyless paper `.env` or refusing to load `PRIVATE_KEY` when `MODE=paper`.

### L4 — Paper DB is 37.9 MB, mostly stale inventory-era opportunity rows
`data/ethereum.sqlite` is 37,924,864 bytes with 163,266 opportunity rows in the last 24h — the paper bot ran inventory mode (which logs every evaluated candidate per tick) until 2026-11-22 ~14:43. `OPP_RETENTION_DAYS` is 7 and pruning runs every 6h, so it ages out by ~11-29. Not a correctness issue; note it only because the file grows ~40 MB/day in inventory mode.

### L5 — Live twin is one failure away from a fail-streak pause
`data/ethereum-live.sqlite` state: `consecutive_fails: 2` (the two METIS withdraw-blocked transfers of 2026-11-21; `MAX_CONSECUTIVE_FAILS` default 3). The next one-sided live failure pauses the Ethereum live twin until `/start`. By design — but the operator should know the streak is still warm.
