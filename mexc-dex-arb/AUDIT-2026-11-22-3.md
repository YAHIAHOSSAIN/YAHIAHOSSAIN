# Audit — MEXC-DEX Arbitrage Bot (full bot, 3rd independent auditor)

- **Date:** 2026-11-22 ~16:15–16:35 Dhaka
- **Auditor:** independent subagent #3 (read-only; no process was started/stopped, no order/withdrawal placed, no file edited except this report)
- **Scope:** `~/workspace/mexc-dex-arb-repo/mexc-dex-arb/` (src, configs, tests), live VPS state (pm2, logs, SQLite read-only, RPC balances), public status pages
- **Code tested:** local `npm test` run by this auditor: **156/156 pass**
- **Live state at audit time:** all 6 pm2 apps online (paper eth, live eth/arb/bsc, status, airdrop tracker)

## Verdict: NOT CLEAN

No Critical finding (nothing found that would lose money on the next trade). One **High** (the Telegram kill switch is unreliable across 5 bots sharing one token) and four **Medium** findings, the sharpest of which is a **remaining Ethereum-only assumption in the transfer path: gas is priced in ETH on BSC** — the same class of bug as the two multi-chain bugs fixed today. The two just-fixed bugs are genuinely fixed and verified live (see "Verified good").

## HIGH

### H1 — Telegram /stop is a lottery: 5 processes share one bot token, getUpdates 409 everywhere

**Evidence**
- `src/telegram.ts` `startPolling()`: every process long-polls `getUpdates` with the same bot token, each with its own offset stored in its own DB. Telegram delivers each update to exactly one polling process — the race winner — and the losers get HTTP 409 `Conflict: terminated by other getUpdates request`.
- Live error logs (this auditor, 2026-11-22 ~16:15) — every process's tail is Conflict warnings with backoff growing to 300 s:
  - `ethereum-live.error.log`: `telegram poll: telegram getUpdates: Conflict: terminated by other getUpdates request ... (retry in 300s)`
  - `arbitrum-live.error.log` / `bsc-live.error.log` / `ethereum.error.log`: same, backoffs 40 s → 80 s → 160 s → 300 s.
- `handle()` only accepts commands in the admin's private chat, but it cannot know which twin the admin meant: a `/stop` is consumed by whichever process wins the poll. There is no per-twin routing.

**Risk:** the kill switch is the safety control for live trading. If the owner sends `/stop` during a bad run, it may stop the paper bot (or the wrong live twin) while the intended live twin keeps trading, or take minutes to be seen at all (backoff up to 5 min per process). Sending alerts (sendMessage) is unaffected — only command delivery is broken.

**Fix:** one bot token per twin (or a single command-router process that owns getUpdates and forwards commands to the right twin).

## MEDIUM

### M1 — Gas is priced in ETH on BSC (transfer path still has a hardcoded ETH assumption)

**Evidence**
- `src/transfer.ts:180-182` — `tick()`:
  ```ts
  const eth = tickers.get('ETHUSDT');
  if (!eth) throw new Error('no ETHUSDT ticker');
  const ethUsd = (eth.bid + eth.ask) / 2;
  ```
  `ethUsd` is then passed as the gas-token price into `evaluate()` (`transfer.ts:335`, `gasUsd(q.gas + APPROVE_GAS, gas.effective, ethUsd)`), into `sellStep`'s booked gas (`transfer.ts:662,676,693,718`: `(Number(gasWei) / 1e18) * ethUsd`), and into the BestOf `gasInOutput` conversion (`transfer.ts:192`).
- On BSC, gas is paid in **BNB** (~$900) not ETH (~$3,000), so every BSC gas cost is overstated ~3.3×. At ~360k gas (swap + approval) × ~1 gwei, the error is ~$0.70–0.80 per $300 trade evaluation.
- The inventory engine does it correctly — `src/engine.ts:289` uses `cfg.chain.nativeMexcSymbol` (`BNBUSDT` on BSC). The transfer engine never touches `nativeMexcSymbol`.
- **False confidence in tests:** `test/upgrade-chain.test.ts:36` is titled *"CHAIN=bsc: the DEX stable is USDT (no USDC conversion) and gas is priced in BNB"* but only asserts `c.chain.nativeMexcSymbol === 'BNBUSDT'` in the config. No test runs the transfer engine on BSC, so the hardcoded `ETHUSDT` in `transfer.ts` was never caught.

**Risk:** conservative direction (no money lost): BSC trades need a slightly bigger real gap to pass (marginal trades wrongly rejected — the error is larger than the $0.60 profit threshold), and booked BSC `gas_usd`/PnL understates profit by ~$0.70–0.80 per trade. Live proof the path otherwise works: BSC logged `WKC: gap 2.34%, size $300.00, exact net -$6.75 (need $0.60)` at 2026-11-22 10:05:14 UTC — correctly rejected, but that net was computed with ETH-priced gas.

**Fix:** in `transfer.ts` `tick()`, read `cfg.chain.nativeMexcSymbol` (like `engine.ts:289`) and pass the native-token price as the gas price; add a transfer-engine test on a BSC chain asserting the gas math uses BNB.

### M2 — Three live twins share one hot wallet with independent nonce managers (nonce collision)

**Evidence**
- All three live twins use the same hot wallet `0x49cD…Ab0` (same `PRIVATE_KEY`), each with its own `TxSender` (`src/dex/txsender.ts`) and its own persisted unresolved-tx store in its own DB (`main.ts:113-116`, `db.getState('unresolved_tx')`).
- The nonce-gap guard `readyToSend()` exists but is only called by the inventory engine (`src/engine.ts:746`). The transfer path never calls it; `transfer.ts` `tick()` only calls `checkUnresolved()`, which sees only its own twin's txs.
- `takeNonce()` reads the chain's confirmed (`latest`) count, which does not include another twin's in-flight tx (sends go through different RPCs).

**Risk:** if two twins reach `sellStep` at the same time, both can sign with the same nonce. One tx mines; the other is rejected/dropped, and the losing twin's `send()` returns `unknown` → `unknownOutcome()` → transfer stuck + trading paused + manual recovery (`/sell` or `/clear`). No double-spend is possible (the chain rejects the duplicate nonce), so the failure mode is a stranded transfer and a paused twin, not a loss. Likelihood is low (a sell needs a ≥2% gap plus a positive exact net, and both twins must sell within the same ~60 s window), but it is a real consequence of the 3-twins-1-wallet design that nothing coordinates.

**Fix:** share one nonce coordinator (one DB/lock for all twins), or serialize DEX sells across twins, or accept the risk explicitly.

### M3 — Config drift: the repo would revert the live Ethereum twin's settings

**Evidence**
- Repo `ecosystem.live.config.cjs`: `MIN_MEXC_VOLUME_USD: '20000'`, `MIN_DEX_VOLUME_USD: '20000'`, **no** `SCAN_MIN_GAP_PCT` (default 3%).
- Running process (`pm2 env 13`, this auditor): `MIN_MEXC_VOLUME_USD: 10000`, `MIN_DEX_VOLUME_USD: 10000`, `SCAN_MIN_GAP_PCT: 2`, `TRANSFER_UNIVERSE_MAX: 100`. The VPS ecosystem file has the $10k/2% values; the repo file is stale.
- The paper-bot config `ecosystem.config.cjs` exists **only on the VPS** — it is absent from the local repo entirely.
- `git status` (this auditor): 12 modified + 4 untracked files, uncommitted since HEAD `4d5fd81` (2026-11-21), including both new live configs, `src/scanner.ts`, `src/transfer.ts`, `src/config.ts`, `CHANGES.md`. Nothing is committed or pushed.
- `.env.example` (modified, uncommitted) says "Live twin (2026-11-22): MEXC $20k + DEX $20k" — stale; live is $10k/$10k.

**Risk:** any redeploy/restart from the repo's ecosystem file silently reverts the Ethereum live twin to $20k volume floors and a 3% gap threshold (fewer trades, different universe), and the paper bot cannot be redeployed from the repo at all.

**Fix:** copy the VPS ecosystem files into the repo as the single source of truth (and commit, when the owner approves a commit).

### M4 — All DEX sends go through public RPCs, not a private endpoint

**Evidence**
- `src/config.ts:59`: `sendRpcUrl` defaults to `https://rpc.mevblocker.io`, with the comment "Private RPC for sending: never the public mempool."
- VPS `.env`: `SEND_RPC_URL=https://ethereum.publicnode.com` (overrides the default for the Ethereum twins); `ecosystem.arbitrum-live.config.cjs:32`: `SEND_RPC_URL: 'https://arbitrum.publicnode.com'`; `ecosystem.bsc-live.config.cjs:33`: `SEND_RPC_URL: 'https://bsc-dataseed.binance.org'`. All three live twins broadcast approval + swap txs via public mempools.
- The pre-flight check (`main.ts:135`) verifies the send RPC's chain id — that guard works — but nothing verifies the endpoint is private.

**Risk:** MEV/sandwich exposure on the DEX sell leg (mitigated by the 30 bps slippage floor in `transfer.ts`, so a sandwich cannot take more than the min-out allows) and dependence on public RPC rate limits for sends. Lower on Arbitrum/BSC than Ethereum, but it contradicts the design note.

**Fix:** point `SEND_RPC_URL` at a private endpoint (Flashbots / MEV Blocker for Ethereum; a private RPC for Arbitrum/BSC) or record the acceptance.

## LOW

### L1 — /status shows wrong numbers on BSC/Arbitrum (hardcoded ETH, /1e6, "USDC")
- `src/main.ts:410` (transfer `/status`): `` `wallet ${(Number(eth) / 1e18).toFixed(4)} ETH, ${usd(Number(usdc) / 1e6)} USDC` `` — on BSC the wallet USDT balance is divided by 1e6 instead of 1e18 (shows ~1e12× too big, labelled "USDC") and BNB is labelled "ETH". Same pattern in the inventory status text (`main.ts:229`). User-facing strings also say "check etherscan" on all chains (`src/dex/txsender.ts:192`, `src/commands.ts:24`, `src/engine.ts:459`) — should be the chain's explorer. Cosmetic only; no money impact.

### L2 — stableRate on BSC should be exactly 1
- `src/transfer.ts:183-185`: `tick()` reads `USDCUSDT` and uses it as `stableInUsdt` for every chain. On BSC the DEX stable **is** USDT, so the correct factor is 1.0; using the USDC/USDT peg (~1.000–1.002) introduces a ≤0.2% error on BSC out amounts and PnL. The peg gate itself (rate within 0.99–1.01) is a fine sanity check on any chain.

### L3 — Arbitrum L1 fee ignored in the pre-trade estimate (and likely in booked gas)
- `L1_FEE_USD` defaults to 0 and is set in no config; `config.ts` comments "0 on Ethereum/Arbitrum", but Arbitrum txs do pay an L1 data fee (typically a few cents). Receipt-level capture exists (`src/dex/txsender.ts` `result()` adds `rawReceipt.l1Fee`), but the Arbitrum config comment itself notes the capture does not apply to Arbitrum receipts (they carry `gasUsedForL1`, not `l1Fee`). Net effect: Arbitrum PnL slightly understates gas. Small and documented in the config; fix by measuring a real Arb receipt's L1 portion and setting `L1_FEE_USD` for the Arbitrum twin.

### L4 — Paper/live separation rests entirely on MODE=paper (latent)
- The paper process holds the real `PRIVATE_KEY` and the real MEXC key, and the shared `.env` has `ALLOW_WITHDRAWALS=yes`. Paper never withdraws only because `transfer.ts` `tick()` returns early for `!live` — but the open-transfer advance loop at the top of `tick()` does **not** check `live`: a paper process pointed at a DB containing an open transfer would execute a real withdraw/sell. Today the separation holds in practice (verified: `data/ethereum.sqlite` has **0 transfers**), and the DB paths are distinct per app. Guard suggestion: skip `advance()` when `!live`, and remove `ALLOW_WITHDRAWALS=yes` from the shared `.env` (live twins already set it in their own ecosystem configs).

### L5 — Silent Ethereum defaults remain (same class as today's two bugs)
- `loadUniverse` `opts.chain` is optional and falls back to `ethNetwork` (`src/scanner.ts`); `dexPrices`/`dexTvl` default to chain `'ethereum'` (`src/scanner.ts`, `src/watchlist.ts`); `TransferEngine.dexPricesFn` is optional and falls back to Ethereum-priced `dexPrices` (`src/transfer.ts`). Production wires all of them correctly today (verified live), but the next caller gets Ethereum silently. Make `chain` required in `loadUniverse` / the engine deps.

### L6 — Startup-failure alert spam
- A twin that fails at startup exits (`main().catch` → `process.exit(1)`) and pm2 restarts it up to `max_restarts: 1000`, sending a Telegram "Bot failed to start" alert on **every** attempt (observed: Arbitrum sent 2 failure alerts in ~12 s during its 2026-11-22 crash loop before it was stopped). Fix: alert once per failure episode, or stop restarting after N consecutive startup failures.

### L7 — evaluate() always adds a full 60k approval gas
- `src/transfer.ts:335`: `gasUsd(q.gas + APPROVE_GAS, ...)` even when the allowance already covers the sale (in which case `approveExact` sends nothing). Overstates gas by up to ~$0.05–0.30 per evaluation. Conservative; minor.

### L8 — Risk limits are per-twin, not shared (known, documented)
- Each live twin has its own DB, own $30/day loss limit and own fail streak; combined live exposure is 3× $300/cycle against one shared MEXC USDT balance ($1,493.98 at audit time). The ecosystem configs already note the 3× $300 exposure (M2 notes). Owner-accepted; noted for completeness.

### L9 — MEXC withdrawal-address whitelist still unverified (verification gap, not a code bug)
- No live transfer has ever completed (arb/bsc: 0 transfers; eth-live: 2 failed transfers from the withdraw-permission era). The first real withdraw on each chain is the first proof the whitelist contains only the hot wallet. The failure mode is safe: a rejected withdraw sells back on MEXC (`transfer.ts` `withdrawStep`).

## Test coverage gaps (multi-chain)

- **No transfer-engine test on BSC/Arbitrum**: the only BSC transfer test is the `stableDecimals` unit test. Nothing tests gas pricing in BNB, `sellStep` PnL with 18-decimal USDT, or the transfer `/status` text on a non-Ethereum chain.
- `test/upgrade-chain.test.ts:36` title overclaims ("gas is priced in BNB") — it asserts only the config value (see M1).
- No test that `loadUniverse` requires a chain, or that a missing `dexPricesFn` fails loudly instead of silently pricing on Ethereum (see L5).
- No test for cross-twin nonce behaviour (see M2) or for the Telegram multi-process conflict (see H1) — both are integration-level.
- `test/scanner.test.ts` (new, untracked) does cover the just-fixed `networkFor` bug with a failing-on-old-code test — good.

## Verified good

- **The two just-fixed bugs are fixed and live.** Arbitrum: `loadUniverse: DEX 24h volume >= $10000 keeps 7/15 tokens` (2026-11-22 10:05:08 UTC); BSC: `keeps 112/241 tokens` → universe capped to 100. `networkFor(chain, …)` is used in both `loadUniverse` (`scanner.ts`) and `buildWatchlist` (`watchlist.ts:104`). BSC stable decimals are threaded from the on-chain read (log: `chain bsc (56), DEX stable USDT 0x55d3…7955 (18 decimals)`).
- **Withdraw safety is sound.** Withdrawals go only to `chain.address` (`transfer.ts` withdraw call); `withdraw_amount` + `wallet_before` are persisted **before** sending, so a crash can never cause a second withdrawal; ambiguous requests are looked up by client id, never re-sent; arrival requires MEXC status SUCCESS **and** wallet growth ≥98% of expected; the sale sells only what arrived (`min(balance, received)`).
- **Aggregator and pre-flight checks.** Kyber is chain-aware (URL path per `kyberName`, router pinned to `KYBER_ROUTER_V2` with `requireAddress`); `main.ts` verifies both `RPC_URL` and `SEND_RPC_URL` chain ids at startup; the config gate blocks transfer on Base; `MIN_ETH_FOR_GAS` refused both new twins before funding (observed twice per chain in the logs) and passed after (0.0178 ETH arb, 0.0376 BNB).
- **L1 fee is captured at receipt level** (`txsender.ts` `result()` adds `rawReceipt.l1Fee`), so booked gas on chains that expose it is honest.
- **Economics check works end-to-end on BSC.** `WKC: gap 2.34%, size $300.00, exact net -$6.75 (need $0.60)` — a 2.34% rough gap correctly rejected after the exact quote.
- **Live numbers independently verified** (this auditor, RPC + read-only SQLite + public API): hot wallet 0.0178 ETH (Arbitrum), 0.0376 BNB (BSC), 0.0303 ETH (Ethereum); paper 25 trades +$17.42; eth-live 2 trades −$5.55 (2 failed transfers); arb-live 0 trades; bsc-live 0 trades; `/api/chains` matches the DBs exactly; `/`, `/ethereum`, `/arbitrum`, `/bsc` all HTTP 200.
- **No non-Telegram errors** in any live log tail at audit time; all 6 pm2 apps online (arb uptime 3 min, restarts 2 — the pre-fix crash loop; bsc 3 min, 0 restarts; eth-live 45 min, 3 restarts; paper 45 min, 17 restarts cumulative).

## Suggested fix order

1. H1 — separate Telegram bot token per twin (or a command router); until then, treat `/stop` as unreliable and stop twins via pm2/SSH when it matters.
2. M1 — price transfer gas in the chain's native token (`cfg.chain.nativeMexcSymbol`) + a BSC transfer-engine test.
3. M3 — sync the VPS ecosystem configs (including the paper `ecosystem.config.cjs`) into the repo; fix the stale `$20k` comment in `.env.example`.
4. M2 — coordinate nonces across twins sharing one wallet (or document acceptance of the stuck-transfer failure mode).
5. M4 — private send RPCs, or record acceptance of public-mempool sends.
6. L1–L7 — small cleanups (status text, stableRate=1 on USDT chains, L1 fee for Arbitrum, live-guard in `advance()`, required `chain`, alert dedup on startup failure, approval-gas estimate).
