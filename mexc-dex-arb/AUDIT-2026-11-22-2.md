## High

### H1 — MEXC client ids collide across the three live chains

**Evidence — `src/transfer.ts:97-98`:**
```ts
const buyCid = (id: number) => `arb${id}b`;
const withdrawCid = (id: number) => `arb${id}w`;
```
Used at `:441` (crash recovery `getOrderByClientId(row.symbol, buyCid(row.id!))`), `:458` (buy), `:488, :521, :538` (withdraw / `findWithdraw` by `withdrawOrderId`).

Transfer ids are per-database (each chain has its own `DB_PATH`), so all three live twins restart their ids at 1 — and all three share ONE MEXC account. MEXC's own SDK doc states `newClientOrderId` must be "a unique id among open orders". Consequences:

1. **Common case — clean failure, no loss:** two twins hold the same transfer id and buy the same symbol (e.g. both on GRT — GRT is in Arbitrum's 7-token universe today; BSC's 100-token universe rescans every 10 min, so overlap is a matter of time). The second `limitOrder` reuses the first twin's client id and MEXC rejects it → transfer fails with "MEXC buy rejected". No money moves.
2. **Dangerous case — cross-twin contamination:** `placeSafely` (`src/engine.ts:74-98`) only looks an order up by client id when the place call throws `AmbiguousRequestError` (timeout/5xx). If twin B's buy times out exactly while twin A holds an open/filled order with the same client id for the same symbol, `getOrderByClientId` returns **twin A's order** and twin B adopts it as its own: `finishBuy` (`transfer.ts:476-490`) reads A's filled qty and cost, marks B `withdrawing` with A's numbers, and then withdraws `min(free, buy_qty × (1−fee))` from the **shared** MEXC balance. Same mechanism for withdrawals: `findWithdraw` (`src/mexc/rest.ts:217-219`) matches by `withdrawOrderId`, so an ambiguous withdraw lookup can adopt the other chain's withdrawal record (needs the same coin + same transfer id).
3. **Crash-recovery variant:** a twin that restarts mid-buy (`advance()`, `:441`) looks up by `buyCid`; if another twin has since reused that id for the same symbol, it adopts the wrong order.

The probability needs three coincidences (same id + same symbol + an ambiguous timeout), so this is High, not Critical — but the ids **will** collide: eth-live already has transfers #1–2 in its DB, arb/bsc DBs start at #1. The inventory engine is immune (`clientId()` at `engine.ts:34` uses `crypto.randomUUID()`), and `sellOnMexc` already uses the random helper — only the transfer buy/withdraw ids are deterministic.

**Fix:** prefix with the chain, e.g. `` `arb-${cfg.chain.name}-${id}b` `` / `...w`, or use the random `clientId()` helper (but then crash recovery by client id must use the persisted id — it already does, via `row.id`, so a chain prefix is the minimal fix). Add a test asserting two chains produce different client ids for the same transfer id.

### H2 — BSC gas is priced at the ETH price

**Evidence — `src/transfer.ts:180-182`:**
```ts
const tickers = await this.d.mexc.bookTickers();
const eth = tickers.get('ETHUSDT');
if (!eth) throw new Error('no ETHUSDT ticker');
const ethUsd = (eth.bid + eth.ask) / 2;
```
`ethUsd` is then used as the native-token price for **all** gas math in the transfer path: `evaluate()` (`:335` `gasUsd(q.gas + APPROVE_GAS, gas.effective, ethUsd)`), the `BestOf` gas conversion (`:192`), and every gas accounting line in `sellStep` / `unknownOutcome` (`:662, :676, :693, :718` — `(Number(gasWei) / 1e18) * ethUsd`). On BSC the gas token is BNB, not ETH.

Live prices checked 2026-11-22 via MEXC public ticker: **ETH $1,713.78, BNB $554.63 → ratio 3.09x**. So every BSC gas figure is overstated ~3.1x. At ~300–400k gas units × ~3 gwei ≈ 0.0009–0.0012 BNB, the real cost is ~$0.50–0.67 but the bot books ~$1.54–2.06 — an overstatement of ~$1.0–1.4 per transfer. Impact: (a) `evaluate()`'s hurdle rejects some genuinely profitable BSC trades; (b) every booked BSC PnL is understated by ~$1. Arbitrum is unaffected (gas is paid in ETH there).

The inventory engine does this correctly — `src/engine.ts:289` uses `this.cfg.chain.nativeMexcSymbol` (BNBUSDT on BSC). The transfer engine is the only place that hardcodes ETHUSDT. `ChainProfile.nativeMexcSymbol` already exists for exactly this purpose.

**Fix:** in `TransferEngine.tick()`, read `cfg.chain.nativeMexcSymbol` (like `engine.ts:289`) instead of `ETHUSDT`. Add a test with a BSC chain asserting the BNB price is used.

## Medium

### M1 — Telegram /stop is unreliable with 5 processes sharing one bot token

**Evidence:** `src/telegram.ts:89-113` — each process long-polls `getUpdates` (25 s) with its own offset stored in its own DB (`main.ts:118-121`). Only one poller wins; the losers get HTTP 409 "Conflict: terminated by other getUpdates request" and back off 5 s → 5 min (`telegram.ts:106-112`).

Live counts from the VPS error logs (grep, 2026-11-22 ~16:10 Dhaka): **ethereum 147 conflicts, ethereum-live 143, arbitrum-live 6, bsc-live 11** (the new twins are only ~10 min old). Sample lines:
```
2026-11-22T10:05:33 WARN telegram poll: telegram getUpdates: Conflict: ... (retry in 300s)
2026-11-22T10:08:26 WARN telegram poll: telegram getUpdates: Conflict: ... (retry in 160s)
```
Consequences: a `/stop` is delivered to **exactly one** process — whichever wins the race. Sending `/stop` once stops one random twin (paper or live, any chain), not all live twins; the user must send it repeatedly and read each reply's tag to see which twin stopped. While all pollers are backed off (up to 300 s), a command can take minutes to be picked up. `sendMessage` (alerts) is unaffected — only command delivery.

**Fix options:** one dedicated command-relay process that owns polling and forwards commands, or a separate bot token per twin, or at minimum document that /stop must be sent once per twin and confirmed by tag.

### M2 — Config drift: repo eth-live config ≠ running process

**Evidence:** repo `ecosystem.live.config.cjs` sets `MIN_MEXC_VOLUME_USD: '20000'`, `MIN_DEX_VOLUME_USD: '20000'`, and **no** `SCAN_MIN_GAP_PCT` (default 3). The running process (`pm2 env 13`, 2026-11-22 ~16:10) shows:
```
SCAN_MIN_GAP_PCT: 2, TRANSFER_UNIVERSE_MAX: 100, MIN_DEX_VOLUME_USD: 10000,
MIN_MEXC_VOLUME_USD: 10000, MAX_TRADE_USD: 300, STRATEGY: transfer, CHAIN: ethereum
```
The VPS `.env` holds the $10k/2% values, so the running twin inherits them — meaning the VPS copy of `ecosystem.live.config.cjs` was edited in place to 10000 and never synced back to the repo (the repo file's comment still says "$20k"). **If anyone redeploys from the repo file, the Ethereum live twin silently reverts to $20k volumes and a 3% gap threshold.** The ARB/BSC configs match their running envs exactly (verified: `pm2 env 17/19` = $10k/2%, correct RPCs). The stale `$20k` claim also survives in the `runTransfer` comment (`src/main.ts`, "100 tokens by volume — MEXC 24h vol >= $20k").

**Fix:** sync the repo `ecosystem.live.config.cjs` to 10000/10000 + `SCAN_MIN_GAP_PCT: '2'` and fix the comment.

### M3 — Paper twin is not pinned to paper mode

**Evidence:** repo `ecosystem.config.cjs` (paper) sets only `CHAIN` + `DB_PATH` per app — no `MODE`. The shared VPS `.env` has `MODE=paper`, `ALLOW_WITHDRAWALS=yes`, `STRATEGY=transfer`. The live twins pin `MODE: 'live'` in their own configs; the paper twin relies entirely on `.env`. If `.env`'s `MODE` were ever flipped to `live` (edit mistake, or a deploy that overwrites `.env`), the "paper" app would start trading **live with withdrawals** on the shared MEXC key + hot wallet.

The paper path itself is clean — verified by code: `tick()` returns via `recordPaper()` before `start()` (`transfer.ts:305-306`), `recordPaper` never touches MEXC writes, the paper DB holds 0 transfers, and `privateKey` is empty in paper mode (`config.ts`). This is purely an operational footgun.

**Fix:** add `MODE: 'paper'` to `ecosystem.config.cjs` env.

### M4 — /status display is wrong on BSC

**Evidence — `src/main.ts`, `transferStatus()` in `runTransfer`:**
```ts
lines.push(`MEXC ${usd(b.USDT ?? 0)} USDT | wallet ${(Number(eth) / 1e18).toFixed(4)} ETH, ${usd(Number(usdc) / 1e6)} USDC`);
```
On BSC, `eth` is the **BNB** balance (labelled "ETH") and `usdc` is **USDT with 18 decimals** — dividing by 1e6 makes the shown balance 1e12× too big. As soon as the BSC wallet holds any USDT (e.g. after a sale, before profits are moved back to MEXC), `/status` will show a trillion-dollar wallet balance. Display-only; today it shows $0.00 because the BSC wallet holds 0 USDT. (The low-balance alert in the same function already does this correctly via `nativeMexcSymbol` + `chain.stable.symbol`.)

**Fix:** use `stableDecimals` for the stable balance and `chain.nativeMexcSymbol` / `chain.stable.symbol` for labels.

## Low

### L1 — `stableInUsdt` on BSC uses the USDC/USDT rate instead of 1
`src/transfer.ts` `costs()` sets `stableInUsdt: this.stableRate` unconditionally, where `stableRate` is the USDCUSDT ticker (~0.999–1.001). `src/pricing.ts` documents `stableInUsdt` as "1 on chains whose DEX stable is USDT". On BSC the DEX output is already USDT, so every evaluation and the loss floor (`holdIfBelowFloor`, `transfer.ts:598`) are off by ~±0.1%. Fix: `stableInUsdt: this.cfg.stableIsUsdt ? 1 : this.stableRate`.

### L2 — Arbitrum L1 data fee is not captured
`src/config.ts` comments `l1FeeUsd` as "0 on Ethereum/Arbitrum" — wrong for Arbitrum, which does charge an L1 data fee. `src/dex/txsender.ts:274-276` adds the L1 fee to `gasCostWei` only when the receipt carries `l1Fee`; Arbitrum receipts carry `gasUsedForL1`, not `l1Fee`, so it stays 0. PnL understates gas by ~$0.01–0.10/tx. Already known to the team (noted in `ecosystem.arbitrum-live.config.cjs`).

### L3 — /api/status top-level fields are misleading for arb/bsc
`status-server.mjs:603-637` (`chainJson`): the top-level `pm2` is the **paper** app's state and `dbOk` comes from `readStatus`, which early-returns `dbOk:false` when a chain has no paper DB (`:236`). So `/api/status?chain=arbitrum` returns top-level `"dbOk":false, "pm2":{"state":"not-found"}` while the nested `live` object correctly shows `dbOk:true`, 0 trades, and live pm2 online. `/api/chains` is correct. The per-chain pages use the nested object, so they render fine — this only confuses API consumers.

### L4 — Crash-loop startup alerts
`src/main.ts` bottom: `main().catch` sends "❗ Bot failed to start" to Telegram and exits(1); pm2 restarts (`max_restarts: 1000`, backoff). A twin that cannot start (e.g. empty universe) alerts on **every** restart — the Arbitrum twin sent 2 such alerts in ~1 min on 2026-11-22 before it was stopped. Consider alerting once, or stopping after N consecutive startup failures. Moot while universes are non-empty.

### L5 — Shared MEXC USDT sizing race (informational)
Each live twin sizes trades from the same MEXC USDT balance (`evaluate()`: `size = min(maxTradeUsd, usdt × 0.99)`). Three concurrent ticks can each commit up to $300 against the same ~$1,494 balance; the later buys fail cleanly on insufficient funds (failed transfer, no loss). No fix required; noted for completeness.
