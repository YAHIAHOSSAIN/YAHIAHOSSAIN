# Pairing-code multi-user dashboard (Muse, 2026-11-23 ~03:24, approved "বানাও বানাও")

Yahia's idea from ~02:10, approved on the voice call: every bot VPS generates a unique pairing code for its owner; the website (arb.alphahelper.online) gets a code-submit box; submitting the code shows THAT bot's live status / trades / PnL on the same page Yahia sees for his own bot. Yahia's own bot gets its own code too.

**How it works:**
1. **Bot side (`src/remote.ts`, new):** on first start each bot instance (one per chain) generates a 24-char random code (`crypto.randomBytes(18).toString('base64url')`, 144 bits) and stores it in its own DB `state` table (`pairing:code`) — never in `.env`, never in git. Announced once in the log + Telegram on first creation. `/pairing` shows the code; `/pairing-new` rotates it (revokes the old code at the receiver first, so it dies at once, then pushes with the new code). Every `INGEST_INTERVAL_SEC` (default 25s) the bot POSTs a public-safe snapshot to `INGEST_URL`: status, hero/today/7-day PnL, per-token, daily, recent 12 trades, transfers, inventory, winners, gaps, depth rejects, DEX-ARB stats, public config, balances, uptime, version. The snapshot is allowlist-by-construction — dex_tx, cex_order_id and transfers.address are never even selected from the DB.
2. **Central receiver (`status-server.mjs`):** `POST /api/ingest` validates the code format, rate-limits (1 push per 5s per code, 60/min per IP), sanitizes the snapshot AGAIN with an explicit allowlist (any secret field — wallet address, key, token, tx hash, order id — is dropped even if a modified bot sends one), and stores it in a separate `remote_bots` table in its own `data/remote-bots.sqlite` (never a bot DB). Only the sha256 of the code is stored, never the code. `POST /api/ingest {action:'revoke'}` forgets a code immediately. Retention 30 days (matches the trade log), pruned on ingest. No snapshot for 2 minutes = offline.
3. **Website:** home page gets a code box + Connect button; codes are saved in the browser's localStorage (max 5) and each shows a compact card (chain, online/offline, hero + today PnL, link to the full page). `/remote?code=...` renders the same premium per-chain page with the live section carrying the remote bot (paper sections hidden). `GET /api/remote?code=...` returns 404 for unknown AND wrong codes alike (no enumeration), and wrong-code guesses are rate-limited per IP (20/min, then 429). **No bot list, no connected-bot count shown publicly** (owner's defaults). **The website sends NO commands to any bot** — no /start, /stop, nothing; bot control stays Telegram-only.

**Design decisions (one code per bot instance, i.e. per chain):** Yahia runs 3 live bots, so he has 3 codes (Ethereum / Arbitrum / BSC) — the website supports several saved codes, each card labelled by chain. A friend running 1 chain has 1 code.

**New env knobs (`.env.example`):** `INGEST_URL` (empty = no push; Yahia's VPS: `http://127.0.0.1:3102/api/ingest`; a friend's VPS: `https://arb.alphahelper.online/api/ingest`), `INGEST_INTERVAL_SEC` (default 25, 10–300).

## Deviations from the prompt (and why)
- **Item 3:** the in-flight tx is persisted in the existing `state` table rather than a new `pending_tx`
  table. Sends are serialized (nothing new is sent while a tx is unresolved), so there is at most one nonce
  in flight, and a single record holds all of that nonce's hashes (the tx and its cancels).
- **Item 4 name:** the helper is `cancelAndConfirm`. It was added for Muse's round-2 review and does what the
  prompt calls `cancelAndSettle`.
- **Item 6 sweep:** `openOrders` is swept for the `WATCHLIST` symbols when `STRATEGY=inventory` and
  `WATCHLIST` is set. With auto-discovery, the watchlist is not known yet when recovery runs, so only the
  cids recorded on the trade rows are checked.
- **IOC:** MEXC's docs list `IMMEDIATE_OR_CANCEL` as an order type, and there is no `timeInForce` parameter.
  But no live symbol lists IOC in `orderTypes`, so closes stay LIMIT plus a confirmed cancel.
